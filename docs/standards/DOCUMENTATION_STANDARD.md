# POG Documentation Standard

**Document ID:** STD-DOC-001  
**Version:** 1.0  
**Status:** Adopted  
**Published:** 2026-08-02

---

# Purpose

This standard establishes the format, organization, and quality expectations for all documentation within the Property Operations Guide (POG).

Consistent documentation improves readability, maintainability, searchability, and long-term usability.

---

# Objectives

Every document should be:

- Easy to understand
- Easy to maintain
- Version controlled
- Self-contained
- Consistent with other POG documents
- Understandable years after it was written

---

# Required Document Header

Every permanent document should begin with:

- Title
- Document ID (when applicable)
- Version
- Status
- Published Date

Example:

```text
# Vendor Evaluation Standard

Document ID: STD-VEND-001
Version: 1.0
Status: Adopted
Published: 2026-08-02
```

---

# Standard Sections

When appropriate, documents should include:

1. Purpose
2. Scope
3. Definitions
4. Requirements
5. Procedures
6. Examples
7. References
8. Revision Notes

Not every document requires every section.

---

# Writing Style

Documentation should be:

- Clear
- Concise
- Objective
- Action oriented

Avoid:

- Ambiguous wording
- Unnecessary jargon
- Personal opinions
- Vendor-specific language unless required

---

# Formatting Standards

Use:

- Markdown headings
- Numbered procedures
- Bullet lists
- Tables where appropriate
- Code blocks for examples

Prefer short paragraphs.

---

# Naming Standards

Use descriptive file names.

Examples:

```
PROPERTY_PROFILE_TEMPLATE.md
VENDOR_EVALUATION.md
INSPECTION_STANDARD.md
```

Avoid spaces in file names.

Use uppercase with underscores for standards and templates.

---

# Versioning

Major Version

Architectural or structural changes.

Minor Version

Additional content.

Patch Version

Editorial corrections.

Examples:

1.0

1.1

1.2

2.0

---

# Cross References

Whenever practical, documents should reference:

- Related Standards
- ADRs
- Decision Log entries
- Idea IDs

This creates traceability throughout the framework.

---

# Quality Checklist

Before publishing a document verify:

☐ Purpose is clear

☐ Scope is defined

☐ Version updated

☐ Formatting follows standards

☐ Cross references included

☐ Grammar reviewed

☐ File placed in the correct directory

---

# Guiding Principle

Documentation should reduce uncertainty.

If a future reader has questions after reading a document, improve the document—not the reader.
